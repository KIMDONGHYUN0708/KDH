# PM/PO 포트폴리오 검수 지침

## 섹션의 역할

- 핵심 과제는 사업 맥락과 고객·운영자가 해결해야 할 상태만 설명한다. 설계 방식과 산출물은 쓰지 않는다.
- 핵심 판단은 선택한 방향과 그 근거만 설명한다.
- 내 역할은 본인이 책임진 범위와 조율한 이해관계자를 설명한다.
- 핵심 난관과 대응은 제약, 판단 근거, 대응, 운영상 영향을 하나의 사례로 설명한다.
- 실행과 상세는 판단을 증명하는 화면·문서만 제시한다.
- 결과·영향은 측정값, 검증 가능한 변화, 후속 확장만 제시한다.

## 핵심 과제 검수

- 고객 여정의 각 단계에는 왜 필요한지와 그 단계에서 확인해야 할 의사결정 정보를 함께 쓴다.
- 여정 라벨만 나열하지 않는다. 예: B2B 학습 단계라면 제품 USP, 확장 라인업, 적용 범위처럼 실제 검토 정보를 명시한다.
- 상단 요약은 핵심 과제 본문을 반복하지 않는다. 요약은 사업 목표, 본문은 고객의 의사결정 조건처럼 서로 다른 정보를 맡는다.

## 카피 검수

- 효율적, 적절한, 체계적인, 원활한, 자연스러운, 고도화 같은 추상어는 금지한다. 무엇을 비교했고 무엇을 줄였으며 어떤 기준으로 판단했는지 쓴다.
- 문장 초반의 쉼표와 불필요한 대조 구문을 피한다. 한국어 문장으로 짧고 단정하게 쓴다.
- 제목은 결론을 말하고 본문은 근거를 보탠다. 같은 주장이나 지표를 여러 섹션에 반복하지 않는다.

## 독자 관점 검수

- 모든 문장은 인사담당자와 현업 담당자에게 보여주는 포트폴리오 문장으로 쓴다. 작성 과정이나 해석상의 변명을 독자에게 설명하지 않는다.
- 결과 수치는 업무 범위와 집계 기간을 사실로 명시한다. “성과로 분리해 해석하지 않았다”처럼 내부 검토자를 향한 단서는 쓰지 않는다.
- 과장 위험이 있으면 성과를 부정하는 문장을 덧붙이지 말고, 본인이 구축·운영한 범위와 측정 기준을 정확히 적는다.

## 증빙·UI 검수

- 화면과 문서는 각각 다른 역할 또는 판단을 증명해야 한다. 같은 여정을 반복하는 증빙은 제거한다.
- 내 역할·판단에는 문제를 해석한 기준과 의사결정만 둔다. 화면, 와이어프레임, 운영 문서, 보고 자료를 역할 섹션에 끼워 넣지 않는다.
- 증빙은 이를 처음 필요로 하는 섹션에 둔다. 문제 구조도는 핵심 과제 뒤에, 난관을 해결한 협업·운영 자료는 대응 바로 뒤에, 화면·정책·시스템 산출물은 실행 단계에 배치한다.
- 실행 상세에는 핵심 서비스 화면 3개 내외와 역할을 증명하는 실행 문서 2~3개만 우선 배치한다. 시스템 구조·인증 처리·보안 검수처럼 하나의 핵심 판단을 서로 다른 자료가 각각 증명해야 할 때만 4개까지 허용한다.
- 추가 자료는 풀덱에서만 보조적으로 사용하며, 맞춤형 제출본에서는 핵심 증빙만 남긴다.
- 프로젝트 간에는 동일한 정보 위계와 카드 문법을 유지한다. 새 UI 패턴은 기존 문법으로 설명할 수 없을 때만 사용한다.

## 최종 점검

- 모든 주장에 실제 행동, 산출물, 결과 중 하나 이상의 근거가 있는지 확인한다.
- 공개 불가능한 수치는 만들지 않는다. 표본, 기간, 측정 기준은 알 수 있는 범위에서 명시한다.
- 읽는 사람이 “같은 내용을 반복한다”고 느낄 수 있는 문장과 이미지는 통합하거나 제거한다.

## 풀덱 프로젝트 차별화

- 9개 프로젝트는 같은 역량을 반복 증명하는 목록이 아니라, 서로 다른 분야에서 발휘한 PM/PO 강점의 포트폴리오여야 한다.
- 각 상세 페이지는 대표 역량을 하나 정한다. 예: 구매 전환 여정 설계, 해외 서비스 이관, 대규모 현장 운영, 스마트 디바이스 연동, B2B 리드 구조, SSO·보안 거버넌스.
- 대표 역량은 헤드라인, 핵심 판단, 난관과 대응, 증빙, 결과에서 같은 사실을 반복하지 않고 서로 다른 근거로 강화한다.
- 새 프로젝트를 작성하거나 수정할 때 기존 프로젝트와 동일한 문제·판단·증빙 구조가 되지 않는지 먼저 비교한다. 같은 역량이 겹치면 해당 프로젝트만의 사업 맥락, 제약, 의사결정, 운영 영향이 드러나도록 중심 사례를 바꾼다.
- 풀덱 전체를 읽은 채용 담당자가 각 프로젝트를 한 문장으로 구분할 수 있어야 한다.
